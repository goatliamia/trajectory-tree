# 上下文持续使用

将上下文视为随任务更新的工作材料。结合当前阶段，区分长期约束、已确认事实、待解决问题、临时输出和可重新取得的原文。关注这些材料是否仍能支持当前决定，以及旧状态怎样被更新。

从上下文增量柱进入时，按图上的响应序号对齐两次请求的构成表，先解释选中来源的变化。只有一个请求可用时，说明该请求的构成。引用构成估算时注明覆盖范围。

**选转折检查构成与组装。** 选持续增长、明显替换、压缩、交接和异常恢复附近的相邻请求，核对来源、进入位置、内容和保留方式。分清追加、替换、移除及压缩，检查旧材料是否仍与新事实并存，再看后续动作是否按新状态推进。这些证据用于解释相应的耗时、用量或返工问题。

**判断增长承担什么工作。** 有些增长积累了产物、约束和可复用证据，有些只是保留大量临时输出、重复说明或已经失效的方案。对后者查后续是否出现反复恢复、重新探索已排除路线、沿用旧状态或遗漏约束。将具体失误与当时实际可见的材料对照，区分没带入、难以取得、没有更新和已有但未正确使用。

**核对已有供给并定位失配环节。** 查出错请求中实际生效的 `AGENTS.md`、系统与开发者提示、工具说明、已读材料及压缩或子代交接，区分四类情况给出对应出口：
1. **关键事实未提供** → 补入对应供给位置（项目事实进 `AGENTS.md`，专项流程进按需 Skill）；
2. **已提供但过期、冲突或难检索** → 直接修改或合并对应源文件条款；
3. **已明确给出但调用仍违反约束** → 分析具体调用参数与触发时机为何失配，调整流程或工具调用方式，不追加同义提醒；
4. **可变运行事实（版本、动态路径、已加载状态）** → 交由运行时状态提供，不写死在静态文档中。

**检查压缩与交接留下了什么。** 核对是否保留了任务目标、已确认决定、当前代码状态、未完成事项、已排除路线和原文取回入口；若压缩后出现大规模重新探索或反复触发 `FS_NOT_OBSERVED`，出口为补充交接摘要模板或在恢复首步先重读目标文件。

**追踪 Skill 的可观察作用。** 分开核对目录可见、正文载入、配套资源/脚本读取及后续动作对具体要求的执行情况，结合确实需要该 Skill 的任务评估它是提供了有效方法、未被触发（需改写 `description` / `whenToUse`），还是正文过长需要拆分为按需 `references/`。

改法落到具体材料：保留关键约束、更新过期状态、合并重复段落、将长原文外置并保留取回入口。缓存组装相关开销按[用量与能力投入](cost.md)核对。
