# Agent 运行轨迹的 Eval 指标与方法

研究笔记 · 2026-11-08

将研究分成两部分。第一部分用宿主已有记录装配事实与关系，计算有明确范围的指标。第二部分用这些事实和指标，由 Agent 按 Eval 判据评估交付、恢复、推进和副作用，程序汇总判定结果。论文、标注和对照服务于研发，用户从自己真实工作的轨迹开始。 [指标框架](metric-framework.md)

## Eval 研究与框架

- **AgentRewardBench 与 AgentBoard。** 前者分别标注任务成功、副作用和无进展重复，再用专家结果校准自动评估。后者通过预先定义、可核验的里程碑计算阶段进展。对真实工作，里程碑取自有效的任务要求与可核对的产物，区分曾经满足与切点时的最终验收。 [AgentRewardBench](https://arxiv.org/html/2504.08942) · [AgentBoard §2.2](https://arxiv.org/html/2401.13178)
- **AgentRx。** v2 在 11 类任务设置的 170 条失败轨迹上，先标注所有失败，再定位导致终局且未恢复的关键一步。方法把轨迹归一、逐步核对约束、记录证据，最后由模型归因。程序检查和模型检查分别登记。其 τ-bench 的准确定位为 42.7%，仍有把末端 guardrail 当成更早错误根因的案例。适合借鉴的是逐步核对与找反证，适用前提包括已知失败和可追踪的后果。 [AgentRx v2，标注、方法与结果](https://arxiv.org/html/2602.02475v2)
- **Inspect Scout 与 Langfuse。** Scout 的 scanner 从日志找特定行为，发现与原日志分存，并用标注数据核对 precision、recall 等。Langfuse 的 observation 级 evaluator 接收映射过的字段，需要子调用或同级动作时由调用方装配。这两者适合参考分析结果的存放、证据范围和研发验证。 [Inspect Scanners](https://inspect.aisi.org.uk/scanners.html) · [Scout 验证](https://meridianlabs-ai.github.io/inspect_scout/validation.html) · [Langfuse 取证范围](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge#data-available-to-observation-level-evaluators)

## 第一部分 装配已有证据

以用户选中的任务、工具枝条或文件为起点，沿现有的 `trajectory_inspect`、`trajectory_read` 和 `trajectory_graph` 取得同一切点的相关记录。保留原始引用，注明证据属于哪个对象和版本，区分原生配对和待核对的候选关系。宿主直接提供目标、效果或验收结果时，保留其判定范围与来源。 [现有工具](trajectory-fields.md)

| 证据 | 可支持的判断 |
| --- | --- |
| 用户要求、目标变更、明确约束 | 确认当时生效的任务和验收范围 |
| 调用与返回、原生错误、检查输出 | 定位动作、当时收到的反馈和检查结果 |
| 补丁、读回、宿主状态、独立验证 | 核实实际效果、验证过的对象和版本 |
| 取消、截断、未记录的结果或状态 | 标明判断缺口，指出需要补查的具体证据 |

## 第二部分 Eval 指标与 Agent 判断

Agent 将证据与判据配对，输出评价单位、结论、支持或反驳的记录和关键缺口。独立状态或验收检查能直接回答时，采用该结果。涉及用户意图、检查范围和过程意义时，由 Agent 判断并说明依据。

| Eval 指标 | 评价单位 | 判据与可汇总的结果 |
| --- | --- | --- |
| **验收达成** | 一条生效的交付要求 | 对照实际产物、约束或验证结果，逐条标记已满足、未满足、待核验 |
| **恢复质量** | 围绕同一阻塞的尝试链 | 从有效反馈到后续行动，再到该阻塞的效果验证。分别汇总已恢复、局部恢复、仍受阻和待核验 |
| **无推进重复** | 围绕同一问题的一组重复尝试 | 比较是否新增信息、排除假设、改变状态或完成必要校验。分别汇总有推进、无推进和待核验的尝试组 |
| **意外或重复副作用** | 有实际影响的状态变更 | 用状态变化与任务意图核对影响。将确认发生的意外或重复影响与任务验收分列 |
| **关键结论的证据支撑** | 一条影响决策的结论 | 核对证据是否覆盖结论的对象、版本和范围，分别统计支持、反驳和待核验 |

### 首项判据 验收达成

1. 从当前有效的用户要求或可定位的验收条件中选取必要项。同一个要求下的多条测试结果仍对应同一评价项。范围不清时标注待确认。
2. 对每项核对产物或检查的对象、版本及覆盖范围。对应检查或状态证据确认通过时标记已满足，确认不通过时标记未满足。检查范围不符、判据改变、版本换过或缺少结果时，按当前要求标记待核验，历史检查照样保留。
3. 展示已满足、未满足、待核验三类数量及其证据。可判定覆盖率为已满足与未满足之和除以适用要求数。所有必要项满足才记通过，有明确未满足项则记未通过，其余情况待核验。适用项无法确定时保留逐项证据。

参考 Inspect 对目标和评分器的分离，轨迹中的实际要求是目标来源。AgentBoard 的里程碑方法适用于可核验的中途状态，最终验收仍按切点核对。 [Inspect Scorers](https://inspect.aisi.org.uk/scorers.html) · [AgentBoard §2.2](https://arxiv.org/html/2401.13178)

## 研发侧验证

### 论文精读转化为验收案例

- **时间与依赖。** Dapper 用显式身份关联跨进程记录，并讨论用发送与接收关系约束时钟差。CRISP 用子跨度时间推断调度与同步边，论文明确说明了依赖数据缺失与时钟漂移的限制。对于相同的记录区间，父步骤可以等待两个子调用，也可以只等待一个，另一个在后台结束。两种情形的区间并集相同。实录时长回归检查所属步裁剪、并行重叠和缺少边界。若要进一步评价等待原因，验收应要求独立的等待或交接证据。 [Dapper](https://research.google/pubs/dapper-a-large-scale-distributed-systems-tracing-infrastructure/) · [CRISP §3、§5](https://www.usenix.org/system/files/atc22-zhang-zhizhou.pdf)
- **恢复与成果。** AgentRx 的案例将早期可恢复的取文失败与后续决定性错误分别标注。AgentRewardBench 将成功、无进展重复和副作用分别交给人工核验。用内部试跑的同一冻结切点准备完整证据和受控删减版，分别问编辑保护后的局部恢复、包装器丢失后台任务 ID、包自检与浏览器验收的差异，以及检索声明与核对完整定理的差异。移除关键返回或验证记录后，预期 Agent 降低结论强度，并指出缺哪项证据。受控删减用于检查对证据的敏感性，再用独立的真实会话复核方法。 [AgentRx 附录 C](https://arxiv.org/html/2602.02475v2#A3) · [AgentRewardBench](https://arxiv.org/html/2504.08942) · [内部试跑](archive/diagnostic-pilot-results.md)

### 验证顺序

1. **先固定评价问题和证据。** 用冻结会话和 Runtime 对照确定问题、适用要求、记录切点及可复核证据。对缺少关键状态或验收结果的案例保留待核验。
2. **用正反例校准方法。** 从内部样本挑出已恢复、换路后进展、成功但无效果、失败却有副作用、必要探索和记录不足的案例。按任务或会话分开调优与复核，同一日志的不同截点归到同一组。研发侧独立标注支持范围、反证、可接受的不同解释和无法判定的情况。
3. **分开测取证和判断。** 核对原文引用可定位率及引用是否支撑结论。对有可靠标签的维度分别报告 precision、recall、关键步骤偏差和判断覆盖率。对证据不足的样本检查保留判断的能力。以同模型、同任务、相近证据预算比较直接读轨迹、程序规则、以及程序取证加方法评估，记录模型和方法版本及开销。
4. **检验建议能否改变工作。** 用盲审核对建议是否具体且能验证，再选已有真实任务对照前后的行动和验收结果。复跑报告保留目标、模型、环境和采集范围。将任务质量、无进展尝试、恢复时间及实际用量分别记录。

### 研发侧联调

首批运行器用同一 DSH 会话的两个切点装配自检和长会话页面证据。每个切点都有完整包和单独隐藏检查返回的对照包。自检判定从已满足降为待核验，导出页探针从未满足降为待核验。宿主页面验收在两种证据条件下都待核验。把自检命令当成通过的负例被评分器拒绝。

四份证据包的调试作答通过了判定和引用检查。参考标注与调试作答来自同一轮研发，独立 Agent 的可靠性留待盲评和未见会话验证。 [运行方式](../experiments/README.md#任务验收-eval)
