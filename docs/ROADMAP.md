# Trajectory Tree 运行时分析路线图

规划草案

用户在 DSH、Codex、Claude Code 或 Pi 中完成真实任务，Trajectory Tree 把留下的记录组织成可探索的执行路径。用户可以选中一次失败、一次文件修改或一处上下文变化，查看相关证据，按需解释，再决定是否把建议带回工作。研发用论文、基准和标注案例验证分析方法，用户从自己的会话开始。

Langfuse 已经支持生产轨迹评估和用户反馈。Trajectory Tree 的产品重点是把诊断接到宿主内的工作流，让用户从图上选中的对象回到原始记录和对话，再沿后续真实执行核对结果。 [Langfuse 生产轨迹评估](https://langfuse.com/docs/evaluation/get-started/online)

## 现有基础

- 四个宿主共用轨迹视图和报告组件。DSH 有分阶段加载、原生目标事件和对话回跳。Codex 可以逐文件查看历史补丁。各宿主保留自己的原始记录、时间单位和数据覆盖范围。 [宿主兼容](host-compatibility.md)
- `trajectory_inspect`、`trajectory_search`、`trajectory_read` 和 `trajectory_graph` 已提供统计、结果筛选、原文及关联读取。`trace-analysis` 和 `context-profile` 已有按问题调查的方法。 [工具字段](trajectory-fields.md) · [过程诊断方法](../skill/trace-analysis/SKILL.md)
- 现有查询已能提供任务要求、工具反馈、文件改动和验证输出。各宿主提供的记录范围不同，Eval 按问题使用可取得的证据。 [工具字段](trajectory-fields.md) · [宿主兼容](host-compatibility.md)
- DSH 的「开放解读」已能用宿主配置的默认模型解释会话中的失败。路径图和解读入口分别计算失败事件。对象诊断可以复用现有读取和模型调用，让同一个切点上的证据同时支撑图和解读。 [路径图投影](../plugin/analysis-view/lib/trace-build.js) · [解读入口](../plugin/analysis-view/lib/index.js)
- 三会话试跑记录了查询负担和原文定位情况，长会话仍出现过取证输出截断。建议能否改变下一次行动，以及改动后能否通过原任务的验收，是后续要单独验证的两件事。 [三会话试跑](diagnostic-experiment-v3-results.md)

## 职责与证据

| 层次 | 交付 |
| --- | --- |
| 运行数据与关系 | 读取宿主原生事件，保留对象身份、原文位置、父子关系、采集来源和覆盖范围 |
| 确定性指标 | 程序在同一切点计算时长、用量、结果和关联，保留单位、来源、分母与覆盖范围 |
| Eval 方法 | 用事实和指标回答任务、阶段或行为的判据。Agent 核对证据，程序汇总判定结果 |
| 可视化与按需诊断 | 在轨迹对象上展示事实与关系。用户选择诊断时，再为模型装配当前问题所需的证据 |
| 改进与验证 | 用户核对、补充或采纳建议。行动由宿主执行并遵循原有权限，后续记录用于复核 |

保留三类结果。**Observed** 是宿主直接记录的事实，例如一次调用返回了错误。**Derived** 是程序计算或匹配的结果，例如观察到同参调用随后成功。**Diagnosed** 是结合任务和证据作出的解释，例如哪一次反馈之后有机会更早调整做法。来源、覆盖范围以及估算口径独立标注，同一个确定性算法也可能使用不完整的输入。

对象诊断绑定宿主、会话或分支、记录切点和原始位置。模型只接收当前问题所需的可见材料，并在同一切点引用证据。解释可包含发生的事、原因、影响、待核实的线索和下一步验证。证据不足时写明还需要哪条记录。诊断的用量和用户反馈单独记录，原任务统计仍使用原有执行数据。

DSH 优先验证完整交互。跨宿主共享方法的输入输出和证据定位，各自的适配器提供可用数据。例如 DSH 的步骤是原生模型步，Codex 的步骤是可见动作。请求级结论在有请求记录的宿主提供，其他宿主可提供动作级分析。 [各宿主的证据口径](host-compatibility.md)

## 分析方法目录

每种方法记录要帮助用户作出的决定、所需证据、关联与计算方式、结论边界和可复核的正反例。六类方法共用轨迹图上的对象与证据入口。

| 领域 | 优先回答的问题 | 需要区分的证据 |
| --- | --- | --- |
| 执行效率 | 哪些尝试取得了有效信息或推进，哪些重复可以减少 | 是否排除了假设、得到新反馈、改变了目标状态或完成了必要验收 |
| 失败与恢复 | 失败反馈出现后，行动怎样改变，结果怎样验证 | 同参重试、换路径后的进展和任务验收分别记录 |
| 信息获取与利用 | 读到的材料怎样关联后续搜索、修改和验证 | 已取得材料、进入后续请求和可能被采用，分别由相应证据支撑 |
| 工具、Skill 与协作 | 工具与参数如何选择，Skill 如何加载，委派与回报如何交接 | 工具返回、Skill 正文和携带记录、父子会话和交接证据 |
| 任务推进与成果 | 用户目标怎样落实到实际产物与验收 | 产物变更、验证范围及待完成的要求。开放任务由模型辅助理解 |
| 上下文管理 | 什么材料增加、保留、压缩或替换，开销如何变化 | 可见构成估算、请求侧证据、真实用量与缓存统计分开记录 |

## 建议的交付顺序

### 1 数据、指标与 Eval 校准

按执行时长、用量、工具结果、文件、成果以及上下文协作维护同一份指标口径。各宿主优先读取原生事实，使用对应的粒度和覆盖范围。确定性指标验证后可直接进入报告和面板，Eval 在同一证据上判断任务影响。 [指标框架](metric-framework.md)

DSH 面板已接入六类确定性指标，支持同切点的整段和逐轮统计。五项 Eval 共用分项结果与覆盖率口径，先用于研发复核；产品侧的模型取证和判定仍待设计。 [面板与计算口径](metric-framework.md#dsh-eval-的六类统计)

先用既有轨迹证据和 Runtime 实验校准任务验收。按任务要求区分已满足、未满足和待核验，写清结论针对的产物、版本与检查范围。随后校准失败恢复、无推进重复和意外副作用。同一个任务上的结论可以各自成立，例如完成了交付但留下重复写入。 [Eval 指标与案例](runtime-analysis-research.md)

研发侧用真实冻结会话、内部对照和独立标注验证。先检查 Agent 能否区分工具返回、真实效果和最终验收，再测关键证据缺失时的判断。面板候选来自通过校准的 Eval 结果，优先呈现每条要求和对应证据。

研发运行器已能对同一切点装配完整证据与隐藏结果的对照包，并分别核对判定和引用。当前有自检与导出页探针两组联调案例。 [任务验收 Eval](../experiments/README.md#任务验收-eval)

### 2 DSH 对象诊断

优先在失败枝条提供按需诊断，再扩到动作和文件。用户从详情看到证据，再决定是否调用宿主模型。诊断返回原对象，并提供可定位的引用。文件诊断按已记录的读取、补丁和相关验证还原形成过程。耗时与重复分析可以沿同一组关系取证。

### 3 上下文、能力与协作

扩展到 Skill 加载与请求携带、上下文增长与替换、子 Agent 交接及整轮目标推进。请求和子会话记录可取得时，再增加对应的归因深度。用可见记录验证读取、携带和后续行为之间的关系。

### 4 改进与复核

先让用户把一条建议带回当前对话，并为下一次真实执行留下验收条件。后续再接入 Agent 主动查询、用户反馈和受宿主权限约束的执行入口。分别记录用户采纳、采取的行动以及实际验收结果。

复核优先选择目标、模型、环境和观测覆盖相近的真实工作。在产物通过相同验收条件的前提下，比较恢复经过时间、重复尝试或返工。一次复跑可以核对一个案例，跨任务的效果判断由多例支持。

## 研究与方法验证

- OpenTelemetry GenAI 的 Agent 和工具 span 可参考命名与关联。其 Agent 语义仍标为 Development，现有宿主字段继续保留各自的证据口径。 [OpenTelemetry GenAI Agent Spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- AgentRx 先记录带证据的约束违反，再由模型归因。Inspect Scout 将行为发现与原始日志分别保存。两者适合参考失败取证和结果追溯。 [AgentRx](https://arxiv.org/abs/2602.02475) · [Inspect Scanners](https://inspect.aisi.org.uk/scanners.html)
- AgentRewardBench 用专家标注校验 Web Agent 的自动评价，并分别考察成功、副作用和重复行为。可以借鉴这种分项校验方法，首批验收仍用真实 DSH 任务和宿主适配案例。 [AgentRewardBench](https://arxiv.org/abs/2504.08942)
