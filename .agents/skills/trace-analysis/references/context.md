# 上下文持续使用

将上下文视为随任务更新的工作材料。结合当前阶段，区分长期约束、已确认事实、待解决问题、临时输出和可重新取得的原文。关注这些材料是否仍能支持当前决定，以及旧状态怎样被更新。

从上下文增量柱进入时，按图上的响应序号对齐两次请求的构成表，先解释选中来源的变化。只有一个请求可用时，说明该请求的构成。引用构成估算时注明覆盖范围。

**选转折检查构成与组装。** 选持续增长、明显替换、压缩、交接和异常恢复附近的相邻请求，核对来源、进入位置、内容和保留方式。分清追加、替换、移除及压缩，检查旧材料是否仍与新事实并存，再看后续动作是否按新状态推进。这些证据用于解释相应的耗时、用量或返工问题。

**判断增长承担什么工作。** 有些增长积累了产物、约束和可复用证据，有些只是保留大量临时输出、重复说明或已经失效的方案。对后者查后续是否出现反复恢复、重新探索已排除路线、沿用旧状态或遗漏约束。将具体失误与当时实际可见的材料对照，区分没带入、难以取得、没有更新和已有但未正确使用。

**建议补充宿主事实前，核对已有供给。** 查出错请求中实际生效的 `AGENTS.md`、系统与开发者提示、工具说明、已读材料及压缩或子代交接。磁盘上存在某份文件，不代表当时的 Agent 收到了它。事实未提供时补到相应供给位置；已提供但过期、冲突、模糊或难以找到时，修对应来源或组织方式；已明确给出却未被动作遵循时，分析调用与约束如何失配，避免再追加同义提醒。现有记录不足以还原供给时保留这一点，不凭一次失败断言模型没收到或遗忘。版本、路径、已加载能力等可变事实优先由运行状态提供并刷新。

**检查压缩与交接留下了什么。** 看是否保留目标、已接受的决定及理由、当前版本、未完成事项、失败路线和原文入口。观察后续是否能继续工作，还是需要大规模恢复。压缩后的体积下降、压缩本身的开销和随后的补读、重复探索放在同一任务段比较。

**分析 skill 时追踪可观察的使用。** 分开记录指令载入、资源读取、配套脚本或工具执行，以及后续动作对具体要求的遵循。纯提示型 skill 可以检查其要求在相关任务中怎样被执行；带资源的 skill 再检查资源实际支持了什么。载入次数或从载入到结束的区间不能替代作用分析。评价增益时，选择确实需要该 skill 的任务，比较关键要求的完成、遗漏和恢复。

改法落到具体材料：保留关键约束，更新过期状态，归并重复记录，将易于定位的长原文外置，同时保留取回入口。验证重点是继续任务所需的信息是否完整、关键约束是否被遵守，以及恢复负担有没有转移到后面。缓存相关的组装问题按[用量与能力投入](cost.md)核对。
