# 用量与能力投入

先从实际用量或费用找到投入集中的阶段，再解释它为何发生。分清一次性准备、每次请求的固定材料、随历史延续的负担，以及额外调用或重做形成的投入。比较的是完成同一任务所付出的总投入。

**沿来源解释持续负担。** 对大段返回，不只看返回当次，还看它在后续请求中保留多久、有没有被重复取回。对大量输出，检查它是必要产物，还是同一计划、进度和解释反复展开。对多次调用，检查它们在推进不同子问题，还是不断补齐上次未取得的材料。需要分析读取范围和返回组织时，按[工具与文件使用](io.md)定位。

**检查能力供给与来源。** 将实际进入请求的工具声明、能力目录及按需展开的详情，与任务需要和真实使用对照。分别报告已安装、可发现、已展开和有调用记录的能力。工具归属以与所选切点对应的注册证据为准，缺失时记为未知。定义体积注明估算口径，调用次数注明观察窗口，低频用途结合实际任务核对。

**在缓存变化处检查材料怎样组装。** 对照相邻请求的用量，核对模型、复用条件、工具声明的内容与顺序、注入和历史裁剪或替换。将日志中确认的变化与对提供方缓存失配原因的推断分开。用同一会话中的相近请求作对照，需要试验时逐项改变待检因素。稳定但较长的配置，与更短却频繁改写的配置，可能产生不同的总投入。

**按来源给策略提示。** DSH 官方 `agent-experience` 强调精简常驻信息、按需披露详情并提供明确的取回入口，收益按整次任务的开销和结果验证。官方工具以宿主支持的用法和加载策略为参照。第三方工具先对照已确认的插件、版本和公开选项。项目自有工具可按证据比较定义或返回结构的改法。归属未知时给出现状和待核对的来源。启停、安装及配置变更由用户决定。

**按改变的层次评估方案。**

- 表达整理：删除确认重复的说明、改进索引和结果组织，保留参数含义、完整性、状态与恢复信息。
- 暴露或加载调整：检查模型能否发现需要的能力、何时真正可用，以及新增的查找、加载和补读是否抵消收益。
- 调整工具用法或项目自有实现时，核对搜索覆盖、默认行为、返回结构与失败恢复，选这些差异可能影响的真实任务验证。

从实际契约差异选择验证场景，例如深层或隐藏目标、分页与截断、部分成功、失败恢复或低频必要能力。比较遗漏、补查与任务完成后的总投入，不能把削弱能力所得的体积降低算作同能力提效。
