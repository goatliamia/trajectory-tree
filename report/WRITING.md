# 报告写作指南

使用用户当前请求的语言撰写正文、标题与图表说明（用户显式指定语言时以指定为准）；引用的日志原文、代码、文件路径、工具名、参数与标识符保持原样。独立 HTML 的界面语言默认自动跟随宿主或浏览器，可通过 `--lang zh-CN` 或 `--lang en` 固定。

## 一份报告的四段式结构

报告是取证完成后的结构化交付。动笔前先核清核心问题、触发原因、后续处理结果与原任务验收状态，按以下四个部分组织 Markdown（渲染时推荐使用 `--template diagnostic`）：

1. **开篇结论与核心指标（Hero 区）**
   - `# 标题` 直接陈述核心诊断结论（例如：“读取保护拦截已于同轮补读恢复，主要耗时集中在第 4 轮全量测试”）。
   - 紧接一段简明背景说明，再用 `> 引用块` 提炼 1–2 句核心判断与处置出口去向。
   - 放一张 `metrics` 图表卡片（绑定 `summary` 表的 3–6 个核心字段，如 `wallMs`、`calls`、`errors`、`errorRate`、`outputTokens`），交代本次分析范围的总体规模。

2. **关键过程与因果证据（`## [pair] 标题` 或普通 `## 标题`）**
   - 围绕造成阻塞、返工或高开销的核心环节展开。先写清“当时掌握什么信息 → 采取了什么调用 → 收到什么反馈 → 后续如何调整并验证”，再紧跟支撑该判断的图表：
     - 涉及多分支、前置依赖、错误传播或恢复汇合 → 用 `flow`（证据绑定流程图）；
     - 涉及单条先后尝试链的原文对照 → 用 `sequence`（步骤取证卡片流）；
     - 涉及并行调用重叠或长调用阻塞位置 → 用 `timeline`（区间甘特泳道）。
   - 已在会话后续通过改参、补读或修代码解决并通过验收的历史报错，直接写明恢复路径与验收结果，不重列为待办。

3. **同切点量化拆解（按需选用 1–2 张统计图）**
   - 图表服务于具体判断，不在文末堆砌无关统计：
     - **核对各工具或处置线索的数量、报错率与耗时分位数** → 用 `table`（绑定 `tools` 或 `findings` 表，自动渲染比率微条与归因状态胶囊）；
     - **比较失败信号、代码执行阶段或轮次耗时排行** → 用 `bar`（绑定 `findings`、`error-types`、`code-execution` 或 `turns` 表）；
     - **展示同一范围内互斥分项的构成占比**（如各窗口占用档位的请求分布、七类上下文构成） → 用 `donut` 或 `stacked`；
     - **观察指标随轮次的起伏或上下文增减** → 用 `trend` 或 `context`；
     - **对比两个明确切点的前后变化** → 用 `comparison`。

4. **处置出口与原链验证（`## [actions] 处置与验证`）**
   - 在 `## [actions]` 章节下使用有序列表（`1. **出口名称：具体对象** ...`），渲染器会自动将其排版为编号行动卡片。每项行动必须落到明确的诊断出口：
     - **无需处置**：属正常探测（如 `rg` 未命中）、单步已自愈或遵从用户取消/拒绝审批，说明记录依据后直接结案；
     - **修复环境与实现**：指明项目自有代码、脚本或配置文件的具体路径与修改方案，并给出在原执行器与原目录下的复跑验证命令；
     - **恢复与观察**：盘点半成品副作用，给出符合保护契约或工作区隔离边界的下一步安全调用；
     - **启停或补齐能力**：**严禁建议修改宿主官方工具的源码、参数定义或内置工具说明（不得改动工具语义）**。涉及官方或扩展工具的启停（关闭或开启）时，必须先阐述清楚该工具承担的职责、主流场景与低频兜底用途，结合用户需求给出配置级关闭或开启建议；
     - **保留可复用方法**：短约束与目录/命令约定给出 `AGENTS.md` 的具体改写或合并草案，多步专项操作流程沉淀到按需加载的 `SKILL.md`。
   - 需要附上详细统计口径或冻结切点元信息时，放在文末 `## [sources] 数据口径与来源` 折叠区。
